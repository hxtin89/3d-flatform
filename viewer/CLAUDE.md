# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Scope

This directory (`viewer/`) is the Vite + TypeScript frontend of a larger point-cloud project. The repo root (`../`) holds the LAZ → PDAL → COPC → 3D Tiles pipeline (bash scripts in `../pipeline/`, driven by `../package.json` `pipeline:*` scripts) that produces the tilesets this viewer consumes. Root `README.md` documents that pipeline; `../.agents/skills/*/SKILL.md` document individual pipeline stages (notably `one-lod-tree`, the core streaming concept below).

One app, one HTML entry: `threejs-test.html` → the **Three.js / WebGPU immersive map app** in `src/threejs-test/`, which is where essentially all the code below lives. `vite.config.ts` auto-opens it and redirects `/` to it.

A CesiumJS viewer used to share this project at `index.html`, with its own copy of the LOD code at `src/` root. That route was abandoned and deleted on 2026-09-09 (see `../plans/plan-remove-cesium.md`); older commits, plans and skill docs still describe it. Outside `src/threejs-test/`, only `dev-hosts.ts`, `maptiler-key.ts`, `types/` and `vite-env.d.ts` remain.

## Commands

```bash
npm run dev            # Vite dev server on :5177, all interfaces, opens threejs-test.html
npm run dev:https      # same but HTTPS (self-signed) — WebGPU on a phone needs a secure context
npm run build          # tsc (typecheck, noEmit) + vite build --base=/livingdashboard/ + prepare-livingdashboard.mjs
npm run build -- livingdashboard-sbb                  # same, built for /livingdashboard-sbb/ instead
npm run preview -- livingdashboard-sbb --port 5177    # preview a build; give the path it was built for
npm run audio:prepare  # regenerate browser audio loops from source-assets/ (writes to public/sounds/)
npx tsc --noEmit -p tsconfig.test.json                # typecheck the app and the *.test.ts files together
```

There is **no linter** in this package, and no general test runner: `npm run bench:verify` runs the `src/threejs-test/*.test.ts` files under `node --test` (type stripping only, so a module a test loads imports its neighbours with the `.ts` extension), and `tsc` is the only static check. `tsconfig.json` (run by `npm run build`, or `npx tsc --noEmit -p .`) checks the app with browser types and leaves the tests out; `tsconfig.test.json` adds the tests and Node's types (`@types/node`). Both are `strict` but `noUnusedLocals`/`noUnusedParameters` are off.

Tiles are served separately by the root pipeline (`cd ..; npm run pipeline:serve` → static tiles on :8081); the dev server proxies `/tiles` there. In practice the Three.js app loads tiles from CloudFront by default (see env below), not the local proxy.

### Runtime configuration

`.env` (gitignored; see `.env.example`) supplies Vite `VITE_*` vars read in `src/threejs-test/main.ts`:
- `VITE_AWS_MEDIA_CLOUDFRONT_DISTRIBUTION_DOMAIN` + `VITE_POINTCLOUD_TILES_FOLDER` → tileset base URL.
- `VITE_MAPTILER_API_KEY` → optional MapTiler satellite basemap.

URL query params (parsed in `main.ts`): `?dataset=` (default `peru-b2-globe`), `?tree=one-lod` (streams the One LOD chain instead of the default APH tree), `?webgl` (force WebGL instead of WebGPU), `?nosnap` (disable ground-snapping), `?modelEditor=1` (enable the in-page model transform editor), `?preset=strong|medium|constrained` (overrides the preset the loader benchmark picks — pixel-ratio cap, view distance, memory budgets, fog quality, ortho density; the benchmark samples while tiles still stream, so a hitch can pin a capable machine to `constrained` — `eagle-bench.ts`, `applyBenchPreset()`), `?dot=tri|quad` and `?feed=pull|inst` (boot with triangle or quad dots, and with the points pulled from a per-tile data texture or drawn as one hardware instance per point; the defaults are `lod.dotGeometry`'s triangle and pulled, Square dots draw quads whatever is asked, and the panel switches both at runtime — `dot-geometry.ts`), `?gputime` (opens the renderer's timestamp query pool, a constructor option and so a load-time switch, for the HUD's GPU row; without it every GPU millisecond figure stays dark, and a steady 0.00 means the browser withholds timestamps — a canvas without area, or Chrome's quantisation, which `chrome://flags/#enable-webgpu-developer-features` turns off), `?diag` (the HUD's diagnostics rows: height against the zoom stop, missing tiles, the levels refinement stopped at, leaf tiles; always on under the Vite dev server), `?freeorbit` (lifts the orbit ceiling, the navigation floor and the zoom stop, so the camera reaches a side-on view of the cloud/map seam; implies `?diag`), `?noorigin` (pins the floating origin at (0,0,0): the same code path with one value different, for an A/B of `origin.ts`), `?stillgate=off` (runs the point-cloud traversal every frame instead of skipping still frames, for an A/B of `still-frame.ts`; `__wild.stillGate` counts frames, runs and why each ran), `?shape=<url>` (loads the protected-parcel outline from another URL, an absolute one too, for a future booking API — `donation-shape-data.ts`), `?benchstress=pulled|instanced` (the loader benchmark's stress primitive for a calibration run, over `eagleBench.stress`; every Start logs the stages to `window.__benchReport` — `eagle-bench.ts`), `?eagleProgress=0..1` (dev server only: holds the loader eagle at that progress, to look at the loader), `?thinning=off` (ship without distance thinning — a load-time switch, not a button, because the per-tile cost is paid on arrival and the cache never evicts), `?tonemap=film|shoulder|none|neutral|agx|aces` (overrides `toneMapping.mode`, default `film`, for an A/B; unknown values fall back to the config — see `tone-mapping.ts`), `?tonemap=off` (boots with the whole tone stage off; with `?colourmatch=off` too it is the pre-tone-mapping shader, for fps comparisons), `?colourmatch=off` (boots with the colour match off: captured point colour and the basemap on `mapBrightness` alone — `colour-field.ts`, `design.colourMatch`), `?ortho=off|half|full` (boots without the drone ortho — no worker, no ortho request — or forces its density whatever the bench preset and the link, as the panel's Half and Full do; `ortho-composite.ts`, `design.droneOrtho`), `?orthokinds` (tints the tiles the ortho was composited into: red where satellite was blended in, blue where the ortho covers all), `?orthocold` (ortho requests skip the browser cache, as on a first visit) and `?orthoreq=<n>&orthojobs=<n>` (ortho requests and upgrades in flight) for timing the ortho with `__three.orthoTrace.report()` (`ortho-trace.ts`), `?vfog=0|1` (boots the volumetric ground fog off or on — `ground-fog.ts`), `?bgclock` (test hook: frames, paced to 60 Hz, and timers from a MessageChannel, so the app runs in a hidden or background tab for automated captures; frame times are meaningless under it, GPU timestamps are not — `hidden-pane-clock.ts`), `?edl=0|1` and `?dof=0|1` (boot with eye-dome lighting or depth of field off or on whatever the config says — both ship on; with both off, `?vfog=0` and the colour grade compiled out no post pass runs, the baseline for fps comparisons; `eye-dome-lighting.ts`, `depth-of-field.ts`), `?grade=0|1` (boots the colour grade off or on whatever `grade.enabled` says; on, a neutral grade with its panel section closed is still compiled out — `grade-editor.ts`), `?sky=0|1` (the physically based sky, sun light and aerial perspective; off is the graded sky and haze curve of before — `sky-atmosphere.ts`), `?shadows=0|1` (the canopy's soft sun shadows — `sun-shadows.ts`), `?clouds=0|1|<preset>` (the sky's dome clouds and their shadows, optionally with a weather preset: clear, fair, scattered, golden, mist, overcast, storm — `sky-clouds.ts`), `?apvol=0|1|ref|dircheck` (the physical sky's aerial perspective from the camera volume, the default, or per pixel with 0; `ref` is a per-pixel reference march and `dircheck` shows the froxel directions' error, both for development — `sky-atmosphere.ts`).

## Architecture — Three.js/WebGPU app (`src/threejs-test/`)

`main.ts` (~6.7k lines) is the orchestrator: it owns the `WebGPURenderer` (falls back to WebGL), the render loop, the HTML preloader, and wires every layer together. The rest are focused modules it composes.

**One adaptive streaming path (the "One LOD Tree").** The central design: a single `TilesRenderer` (`3d-tiles-renderer`) traverses one external 3D-Tiles chain that links density bands **Overview p02 → Explore p10 → Detail p100** through nested `tileset-one-lod-tree.json` sidecars. One renderer owns traversal, downloads, CPU cache, and GPU residency for every zoom level — there is no separate loader per LOD. See `../.agents/skills/one-lod-tree/SKILL.md` for how the pipeline builds that chain and its invariants.
- `streaming.ts` — wraps `TilesRenderer`, sets cache/GPU/download budgets, installs plugins. Notable: a custom `ViewerRequestVolumePlugin` (because the current 3DTilesRendererJS release ignores `viewerRequestVolume`, without which p10 and p100 refine together and defeat the single-tree design), a `FrustumMaskRegion` (`LoadRegionPlugin`) that culls out-of-mask tiles from *fetch/refine/render*, and per-tile (not shared) materials because `UnloadTilesPlugin` disposes a hidden tile's material.
- `tile-retry.ts` — 3d-tiles-renderer never asks again for a tile whose download failed while that tile sits in its cache, and a tile under the camera is never evicted, so one dropped connection left a permanent hole (for the basemap, kilometres of sky through the ground). Every `TilesRenderer` (points in `streaming.ts`, basemap in `globe.ts`) is wrapped: a failure that is not a 4xx refusal takes the tile out of the cache and asks for it again, after 2 s and twice as long after each further failure, up to a minute. Node-tested.
- Fidelity — one error target, no feedback controller (`adaptive-quality.ts` is gone). `lod.sse` (4, a point spacing in CSS pixels; the design panel's slider changes it) holds at every camera range, because the renderer's error quotient already divides by distance. `updateStreaming()` in `main.ts` hands it to the streamer, and only the brakes raise it, both about time rather than distance: `lod.bootSse` (256) while the loader is up, `lod.flightSse` (64) during a camera flight, eased back in log space over `lod.flightSseRampMs` after landing (`flight-quality.ts`, node-tested). The initial point-of-view load runs unbraked; the render options can switch the brakes off (`sseBrakes`) or force every leaf in the frustum (`leafLoading`). Foveation (`foveation.ts`), the viewing-angle cosine (`view-angle.ts`) and the view-axis depth (`view-depth.ts`) each multiply a tile's error, all off by default. Nothing reads frame times to change the detail at runtime; the loader benchmark sets the start preset once (see below).
- `manifest.ts` — reads `area-manifest.json`: the ENU→ECEF `rootTransform` that places local-ENU point coords on the WGS84 globe, survey bbox, and the derived One-LOD-Tree dataset path.

**Placement / camera.** `globe.ts` builds the WGS84 globe + basemap; the manifest `rootTransform` positions the local point-cloud ENU frame onto it. `keyboard-navigation.ts` provides frame-rate-independent pan/zoom that scales with camera range. All flight/camera/marker tuning lives in `config.ts`.

**Environment & atmosphere.** `environment-layer.ts` (largest layer) drives a Peru-timezone daylight cycle (sky/fog/light colors, sun direction), a performance-`tier` classifier (`constrained`/`balanced`/`strong`), and volumetric cloud state. Clouds are TSL (Three Shading Language, `three/tsl`) raymarched volumes — see `tsl-raymarch.ts`, `cloud-noise.ts`, and the `MeshBasicNodeMaterial`/node-material usage. `rain-layer.ts`, `audio-layer.ts` (day/night/rain ambient loops with fades), and the point-cloud daylight grading in `point-cloud.ts` all react to the same daylight/tier state. `atmosphere-haze.ts` adds distance haze (`scene.fogNode`, which takes precedence over the `scene.fog` distance fog) and a horizon-to-zenith sky (`scene.backgroundNode`, over `scene.background`), each with its own switch that sets the node to null. `ground-fog.ts` ray-marches the volumetric ground fog, a post pass in the depth-of-field pipeline that reads the scene depth: density from one tileable 2D noise texture for coverage, billows and erosion plus a fixed 64³ 3D texture for the height detail (`noiseSource: '3d'`, the default; `fog-noise.ts`, baked in `fog-noise.worker.ts`, inspected and edited in `fog-noise-editor.ts`), light from the scene's sun with a Mie / Rayleigh phase and multiple-scattering octaves (`fog-optics.ts`); steps and resolution per quality preset in `config.ts`. The march's jitter moves every frame and `fog-temporal.ts` blends each frame into the previous result (`volumetricFog.temporal`, on by default): reprojected with the camera, read only from texels whose depth a frame ago matches, and clamped to the current neighbourhood's spread, so the sampling grain averages out instead of boiling under a moving camera. The output look lives in `tone-mapping.ts` (`film` by default; every film part compiles out when switched off). After it comes the colour grade (Design → Colour grade, config `grade`): the whole grade — white balance, lift/gamma/gain/offset wheels, contrast and pivot, saturation, vibrance, curves, hue curves, split toning, roll-off and an imported `.cube` look — is baked on the CPU into a half-float 3D LUT (33³, or the refined lattice an imported cube needs) and sampled once per pixel on the displayed frame, after the tone curve and the sRGB encode, in the final quad (`depth-of-field.ts` `setOutputStage`, `grade-output.ts`); about 0.01 ms whatever the controls, measured in `../plans/grade-editor/plan.txt` §7. Neutral with the section closed it is compiled out; switching between the two rebuilds the post shaders once (9 node builds with DoF and EDL on), moving a control never does. The maths is pure and node-tested (`grade-model.ts`, `grade-curves.ts`, `grade-bake.ts`, `cube-format.ts`, `grade-state.ts`), the bake runs in `grade-bake.worker.ts` (same code on the main thread as fallback: `grade-bake-host.ts`), and `grade-editor.ts` / `grade-editor-logic.ts` / `grade-widgets.ts` are the panel. `__three.grade` is the console handle (setStage, bake, setSplit, stats, editor). Before any of that, the colour match (`colour-field.ts`, `design.colourMatch`) evens out the survey's flight-block colour drift and matches the cloud to the basemap at landscape scale, from a small per-dataset gain texture in `public/colour-field/` that `../pipeline/build_colour_field.py` builds (it needs this dev server running, for the MapTiler proxy). The same run (`--ortho <tileset id>`) builds the drone ortho's fields and tile-kind grids, and `ortho-composite.ts` paints the drone ortho (~15 cm a pixel) into the satellite tiles it covers — in a worker, into the tile's own texture once the tile has settled on screen (only two requests at a time while the basemap or the point stream still loads, eight after; `ortho-upgrade.ts`), so the basemap refines as fast as without it and the ortho adds downloads and one in-place upload per upgraded tile, but no mesh, texture, draw call or shader code (`ortho-plan.ts` decides which tiles, `ortho-compose.worker.ts` blends).

**Sky package.** `sky-atmosphere.ts` renders Hillaire's atmosphere (the model, tested, in `atmosphere-model.ts`) into small fragment-pass lookup tables, draws the sky with a full-resolution sun disc as `scene.backgroundNode` and aerial perspective as `scene.fogNode` (both through `atmosphere-haze.ts`'s physical mode; the aerial perspective comes from a camera-frustum volume — 32 × 32 froxels × 32 distance slices in one atlas, drawn in one fragment pass when the view moves, read with two fetches per pixel, arithmetic in `aerial-volume-math.ts` — or per pixel with `?apvol=0`), and captures the sky's irradiance for the light uniforms. The points and basemap are relit by it (`effects.sunLight` in `point-cloud.ts`: no normals, so a side-light blend), the fog takes its sun and sky light from it. `sun-shadows.ts` splats a fixed share of every loaded tile's points from the sun into an additive optical-depth height-moment map fitted to the sphere-fade dome (per-tile proxies in a private scene, a caster graph from `point-cloud.ts`; nothing but the dome's falloff follows the camera, so the shadows hold still as it moves), blurred in metres; points, basemap and every fog step read it. `sky-clouds.ts` bakes one procedural cloud field (`sky-cloud-noise.ts`, a worker) into a progressive, cross-faded dome panorama and a cloud-shadow map the same receivers read; weather presets live in `config.ts` (`skyClouds.presets`). `sky-panel.ts` builds the Sky & sun, Sun shadows and Sky clouds panel sections; `main.ts` `applySkyPackage()` keeps their switches consistent. Every part compiles out when switched off.

**Field assets.** `field-model-layer.ts` loads GLTF props (tower, boat — offsets in `config.ts`), optionally driven by `model-transform-editor.ts` when `?modelEditor=1`. `marker-layer.ts` renders interactive hotspots that trigger Bézier camera flights.

**Loader = benchmark.** `eagle-bench.ts` renders a real point-cloud eagle during load whose density follows load progress; it measures frame time to pick a starting performance tier so weak hardware never discovers its limits through jank mid-session. `stats.ts` is the FPS meter.

**`config.ts`** is the single source of product-facing tuning (flight paths, navigation clearances, keyboard speeds, cloud/atmosphere/audio/rain parameters, field-asset transforms) — all values in metres and milliseconds. Prefer changing constants here over hardcoding in layers.

### Conventions

- Layer modules export a `createXxxLayer(...)` factory returning an interface with `update(...)` / `dispose()`; `main.ts` calls `update` each frame and `dispose` on teardown. Follow that shape for new layers.
- WebGPU is primary (`three/webgpu`, `three/tsl`); code must degrade to WebGL (`?webgl` and automatic fallback). Don't assume WebGPU-only features without a fallback.
- UI strings are English throughout — loader, HUD, panel labels and their
  descriptions, status and ARIA text. They used to be German; if you find a German
  string in user-facing text it is a leftover, not a decision. Source comments are
  a separate matter and some are still German.

## Deployment

`npm run build` targets an Apache mount at base `/livingdashboard/`; an argument (`npm run build -- <path>`) builds for another path on the same domain, so copies can be deployed side by side. `scripts/dashboard-base.mjs` holds the path for build, preview and the check alike. Vite builds the single `threejs-test.html` entry; `scripts/prepare-livingdashboard.mjs` then copies it over `index.html` so the app is the default page, checks both files for root-relative asset paths that would escape the base, and writes the `.htaccess`. Keep that base behaviour intact if you touch the build.
